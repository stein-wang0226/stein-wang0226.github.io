<h2>Motivation</h2>

<p>当前 AI agent 在生物信息学领域的能力评测面临一个根本矛盾：高质量的评测任务需要领域专家花费大量时间手工构造（一道好题可能需要一位博士生一周的时间），但规模化评测却需要数百道覆盖不同分析轴的任务。这使得评测集的构建成为 benchmark 迭代的瓶颈。</p>

<div class="glossary"><em>术语约定：GEO（Gene Expression Omnibus）是 NCBI 的公开组学数据仓库，每条研究以 GSE 编号标识；docker/podman 是当前本地隔离执行 solver / verifier 的沙箱口径；Terminal-Bench 3（简称 TB3）是 Harbor 框架的标准化评测任务格式；Codex CLI 是以非交互模式调用 LLM 的命令行工具。</em></div>

<p>现有方法的不足在于：人工出题无法保证判分的确定性和可复现性；简单的"答案查表比对"容易被 reward hacking 绕过；题面过度指定统计方法则会退化为"翻译题"——agent 仅需机械编程而无需科学判断。我们需要一条能批量产出"难度来自科学而非体积"的任务的自动化链路。</p>

<h2>Key Insight</h2>

<p>我们的核心观察是：评测任务的构造本身可以被建模为一条信息逐步丰富、逐步冻结的流水线——类似于工业装配线上的"站位"设计。每个站位（LLM 角色）只接收它需要的信息、只产出结构化的落盘产物，而站位之间的信息隔离恰好构成了题目安全性的天然屏障。</p>

<p>用一个类比：这像是一家出版社的编辑流程——选题编辑（explorer）筛选稿件，审稿人（auditor）做深度评审，作者（author）撰写正文，校对员（gates）做格式检查，匿名审稿人（solver）盲审，终审编辑（judger）下最终结论。每个环节看到的材料不同、权限不同，但产物环环相扣。</p>

<h2>Approach</h2>

<h3>方法总览</h3>

<p>GEO-Harbor-Bench 将 NCBI GEO 公开研究转化为 Terminal-Bench 3 风格任务。核心原则只有三条：角色隔离、静态门禁前置、跨模型评审。</p>

<h3>评审 rubric 体系：每个站位的判分维度</h3>

<p>质量控制采用<strong>分层裁决</strong>：越靠近昂贵盲测，判据越严格；每个站位只回答一个可被证据支撑的问题。</p>

<table>
  <thead><tr><th>站位</th><th>判分者（模型）</th><th>评审维度</th><th>裁决规则</th></tr></thead>
  <tbody>
    <tr><td>Phase 1 · 候选打分</td><td>geo_explorer（gpt-5.5）</td><td>5 维 × 1–5 分：data_access / design / depth / size / axis_fit（满分 25）</td><td>total ≥ 18 进审计</td></tr>
    <tr><td>Phase 2 · 研究深审</td><td>study_auditor（gpt-5.6-sol）</td><td>七道硬门 + proposal 七维预评 + quality_score</td><td>七门全过且 quality ≥ 80 → proceed</td></tr>
    <tr><td>Phase 3 · 题面早评（盲测前）</td><td>rubric judger（claude-opus-5）</td><td>只看 difficult / well_specified / outcome_verified：题面是否清楚、是否按结果判分、是否值得进盲测</td><td>well_specified / outcome_verified 不达标直接 revise；difficult 用作难度预警，不烧沙箱</td></tr>
    <tr><td>Phase 3 · 零 token 静态门禁</td><td>确定性脚本（无 LLM）</td><td>10 道：skill 三件套（lint / validate / checklist）、instruction_gate 泄漏计分、题面质量、结构检查、environment 可重放性、oracle 自检、test.sh 信号、calibration 覆盖、calibration-verifier 一致性、dockerfile</td><td>失败 → fixes.md 打回 author，零成本前置拦截</td></tr>
    <tr><td>Phase 3 · 全量评审（盲测后）</td><td>rubric judger（claude-opus-5，异族）</td><td>proposal 7 维 + implementation 4 关键项 + trial_analysis 失败归因</td><td>release 关键维度全 accept 才 pass；difficult 进入难度分桶，不单独阻塞 release；3 轮不过换候选</td></tr>

<p><strong>当前实现与 rubric 主干对齐。</strong><code>run_judger.py</code> 使用 TB-Science proposal 七维、implementation 四关键项和 trial-analysis 八类归因；<code>gates.py</code> 负责零 token 门禁和 Harbor package 自包含验收。准入上更保守：规格、可验证性、可复现、隔离和 tests 对齐是硬门；<code>difficult</code> 主要用于难度分桶，不拿“太简单”单独否定一个已自洽任务。</p>

<p><strong>核心 rubric：proposal 七维 + implementation 四关键项。</strong>每一维都写明正例锚点、反例锚点与一票否决条件，把「看起来合理」压成可引用证据：</p>

  <thead><tr><th>维度</th><th>正例锚点</th><th>一票否决条件（reject_if）</th></tr></thead>

<p>implementation 层在当前代码里落为四个 release 硬门：反作弊隔离、功能性判分、确定性复现、tests 与 instruction 对齐。</p>

<p>rubric 的作用是把主观判断压成证据判断：每维都有正例锚点、反例锚点和一票否决线；触线即回到修订链路。</p>

<h3>题面早评：盲测之前的质量前闸</h3>

<p>早评是盲测前的低成本质量前闸：只判断题面是否值得进入昂贵沙箱，不看 solution/tests。</p>

<ul>
  <li><strong>只评三维：</strong>difficult、well_specified、outcome_verified；没有盲测轨迹的维度不强判。</li>
  <li><strong>硬阻塞：</strong>well_specified 不达标直接打回，因为这通常意味着“题面开放空间大于校准覆盖”。</li>
  <li><strong>防泄题：</strong>评审工作区白名单构建，solution/ 与 tests/ 不进入；反馈也不能写具体方法、参数、阈值。</li>
  <li><strong>价值：</strong>把规格不清、配方泄漏、难度造假挡在盲测前，不烧沙箱、不消耗盲测预算。</li>
</ul>

<h3>盲测失败的八类归因路由</h3>

<p>盲测失败后不直接“重写一遍”，而是先进入 trial_analysis 路由。八类归因对应不同修复动作：</p>

<ul>
  <li><strong>task_specification：</strong>题面不清或目标不闭合 → 修题并重新冻结。</li>
  <li><strong>oracle_discoverability：</strong>公开证据不足或入口难找 → 补证据/改任务，不强行放行。</li>
  <li><strong>verifier_correctness：</strong>判分器误拒合法解 → 修 verifier 与校准包络。</li>
  <li><strong>reward_hacking：</strong>存在投机路径 → 加固反作弊与输出契约。</li>
  <li><strong>difficulty_crux：</strong>失败来自真实科学难点 → 可作为有效难度保留。</li>
  <li><strong>near_miss：</strong>接近正确但落在边界 → 扩展多路径校准或收紧容差说明。</li>
  <li><strong>low_timeout：</strong>资源/时间预算不足 → 调整预算，不当作科学失败。</li>
  <li><strong>refusals：</strong>题面触发拒答或误解 → 改写题面表达。</li>
</ul>

<p><strong>实证：</strong>247 个 proposal 评审记录显示，difficult 的 uncertain 可弱接受；well_specified 的 uncertain 是硬阻塞（0/8 通过），通常意味着题面自由度超过校准覆盖。</p>

<h3>关键设计决策</h3>

<p><strong>为什么拆成多个角色？</strong> 为了物理隔离信息：solver 看不到 tests/solution，评审员也不能从 oracle 反推答案。</p>

<p><strong>为什么需要双代码路径？</strong> 这一步不是 NOP，也不是把 solution 当作盲测结果；solver 只提交输出，verifier 在 docker/podman 中对照冻结 oracle / accepted paths 复算，solution 只用于参考路径自检，避免同源 bug 造成“永远满分”的假题。</p>

<p><strong>为什么前置门禁重要？</strong> 零 token 门禁在沙箱前拦截结构错误、配方泄漏和依赖缺失，避免无效盲测。</p>

<h3>交付产物：task package 目录结构</h3>

<p>最终交付的是自包含 Harbor task package。核心原则很简单：<strong>考生只看题面和公开数据；答案、判分器和出题证据随包保存，但在盲测时物理隔离。</strong></p>

<div class="artifact-block">
  <p class="artifact-caption">Harbor package 根目录：<code>tasks/&lt;slug&gt;/author/task_package/</code></p>
<pre>tasks/&lt;slug&gt;/author/task_package/
├── instruction.md                 # solver 可见：题面与输出要求
├── task.toml                      # 机器可读契约、资源预算、artifact 声明
├── environment/
│   └── data/                      # solver 可见：公开 fixture 与 checksum
├── solution/                      # 盲测物理排除：oracle 参考解
├── tests/                         # 盲测物理排除：verifier、test.sh、独立数据副本
└── authoring/
    ├── calibration-summary.json   # 合法路径 / known-wrong / 校准边界
    └── provenance/                # GEO 来源、深审结论、数据转换记录</pre>
</div>

<p>导出时丢弃逐轮草稿、盲测留档和临时探针；保留题面、运行环境、判分器、参考解法与 authoring 证据链。这样上游既能直接运行任务，也能复核“这道题为什么成立”。</p>

<h2>Case Study: CRISPR-MHC-II-Screen 合成任务示例</h2>

<p>这个 case 主要展示流水线最终合成出的 Harbor 任务长什么样：它不是论文复述，也不是固定代码配方，而是把真实 GEO 研究转化为可盲测、可判分、可复核的任务包。</p>

<h3>合成后的题面核心</h3>
<div class="artifact-block">
<pre>任务背景：
GSE304150 是一个围绕 MHC-II 表达调控的 CRISPR 全基因组筛选实验。
输入数据为 sgRNA read count matrix，覆盖 A375 与 WM115+IFNγ 两个细胞设置，
并区分 MHC-II high / low 细胞群体。

输入：
- raw count matrix：77,441 guides × 10 samples
- sgRNA-to-gene annotation
- sample metadata：cell line、MHC-II 分选状态、replicate

目标：
从原始计数出发，识别促进或抑制 MHC-II 表达的候选调控基因。
solver 可以自行选择合理的归一化、效应量估计和统计检验方法，
但必须输出可复算的 gene-level 结果。

输出：
- gene-level ranking
- effect direction / effect size
- significance or support evidence
- short interpretation of top hits

判分重点：
结果是否能稳定恢复 MHC-II 通路核心信号，并满足输出 schema 与复算约束。</pre>
</div>

<h3>为什么这个任务成立</h3>
<ul>
  <li><strong>真实科学问题：</strong>从 CRISPR screen 中识别 MHC-II 表达调控因子，问题本身具有清晰生物学意义。</li>
  <li><strong>输入可复算：</strong>任务基于 sgRNA 级原始计数矩阵，而不是只给最终 hit list。</li>
  <li><strong>开放但可判：</strong>不指定唯一统计配方，保留 solver 的方法选择空间；同时用 gene-level ranking、效应方向和显著性证据约束输出。</li>
  <li><strong>生物学 sanity check：</strong>HLA-DRA、RFXAP、RFXANK、RFX5、CIITA、CD74 等 MHC-II 相关信号应在结果中得到合理支持。</li>
</ul>

<h3>合成过程只保留关键转折</h3>
<p>候选审计确认原始计数矩阵可得；早版题面因方法写得过细被门禁拦截；修订版只保留科学目标、输入输出契约和判分边界，并登记多条合法解法路径。最终任务通过盲测、verifier 复算与评审闭环，形成自包含 Harbor package。</p>

<h2>Production Pipeline Update：解决双端矛盾并提高有效产出</h2>

<div class="tldr">
  <strong>更新结论</strong>&nbsp;&nbsp;最新生产链路已经从“单题修补”升级为“ready → done”的连续产线。ready 指原始数据完整、通过深审、可进入生产闭环；done 指完成验证和 Harbor package 自包含验收。当前本地已有 700+ ready 任务和 413 个 done package；ready→done 成功率从早期约 10% 提升到保守 <strong>70%+</strong>。
</div>

<h3>当前新链路：从候选发现到 ready/done 沉淀</h3>

<p>新链路拆成六步：候选供给、审计筛选、Author 造题、校准覆盖、闭环验证、交付登记。题面只写科学目标，不泄漏统计配方。</p>

<div class="artifact-block"><pre>GEO/SRA 候选
  → 审计筛选：数据可得、科学问题成立、输出可判
  → Author 造题：只写目标，不泄漏方法配方
  → 校准覆盖：合法路径接受，错误路径拒绝
  → 闭环验证：docker/podman 中 verifier 复算 + 证据链复核
  → ready 池：原始数据完整、通过深审、可进入生产闭环
  → done 入库：Harbor package 自包含验收通过</pre></div>

<p>关键变化：每步都有可复核证据；失败能定位到数据、题面、校准、verifier、基础设施或科学设计，而不是笼统归因给模型。</p>

<h3>主要卡点：双端矛盾如何解决</h3>

<p>最大卡点是双端矛盾：题面要开放，verifier 又要确定性判分。写太细会变成配方翻译题；写太开放又会导致校准覆盖不足。</p>

<p>解决方式是拆开治理：题面保留合理自由度，校准登记可执行路径。reference、accepted、known-wrong 与边界 case 一起约束 verifier，既保住科学难度，也避免隐藏唯一答案。</p>

<h3>真正有效的优化</h3>
