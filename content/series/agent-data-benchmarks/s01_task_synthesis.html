从“生成问题”到“生产可学习任务”

Agent数据合成的关键产物是一个可重复执行、结果可独立检查的任务系统。问题文本、依赖环境、初始状态、可见资源、solver权限、verifier和轨迹必须形成一致的合同；否则“失败”无法区分能力不足、环境损坏与验收错误。

生产单位最小内容常见错位
SourceIssue、commit、论文、需求或专家protocol；来源与许可Source记录数当作可执行任务数
Environment固定依赖、数据、构建与初始状态镜像构建成功就称任务正确
Task问题、环境、独立verifier、资源与时间限制一个环境的任务变体当作独立能力family
Episode / trajectory策略版本、动作、工具结果、产物、reward和成本同任务重复采样数量当作覆盖扩张

公开评测集用于固定留出；合成资源可有自己的held-out split，但不能因此直接替代最终benchmark。评分协议见第02章。

从路线比较到科学任务方案：第03章选GSE52778/airway说明来源冲突、供体配对、study级切分、隐藏参考和独立verifier；第04章连接轨迹准入、SFT/RL与工业集群。任务、环境和轨迹数量分别记录；本轮只交付合同与设计，尚未构建真实task package。

路线的选择应由缺口决定

已有真实问题但环境不稳定，优先做SWE-Gym / daVinci式环境工程；repair任务缺量，用commit逆向与mutation，但控制分布偏移；目标技能在旧issue中缺失，用NexForge / 专家protocol；训练停滞时，用EvoSyn分析生成空间覆盖与预算；reward稀疏而验收昂贵时，学习critic辅助筛选，并保持独立可执行验证。

同一recipe可能结合多条路线。任务数量不代表information gain：同repo的近重复patch、模板变体及同策略重复rollout应分别计数。

Harbor任务合同：让solver与verifier看到不同资源

Harbor提供运行与交接约定；它本身不是benchmark。任务包至少包括说明、配置、environment、参考solution与tests。[20] 将独立verifier放入干净sandbox时，必须显式交接允许的产物；不能假设solver随手写入的任意文件或运行状态自动出现在验收环境。[21]

task/
  instruction.md          # solver可见：目标、输入、交付约束
  task.toml               # 环境 / agent / verifier资源与deadline
  environment/Dockerfile  # 固定base image与依赖
  solution/solve.sh        # 校准用oracle，solver不可见
  tests/test.sh            # 独立验收入口
  tests/check_result.py    # 行为、数值或状态检查

audit/                    # 此处为建议的审计伴随产物，非Harbor必需字段
  source.json             # 来源、license、repo/revision及family
  calibration.json        # oracle / bad / alternative结果
  artifact-manifest.json  # 允许交接的文件与hash

这是目录示意，没有随本文发布一套已校准task。审计字段属于建议扩展；实际配置名称按所用Harbor版本的schema核对。

边界最低检查典型错误
构建与reset离线可重建、冻结输入、清洁初始状态、重复reset一致残留产物、未来git、依赖更新改变难度
solver可见面可见目录 / 工具 / 网络白名单，排除答案和隐藏testssolution、test patch或缓存含参考答案
产物交接明确文件、diff或状态；干净verifier重建后检查只在solver环境中test通过，交付物不能复现
验收独立性oracle通过；bad控制失败；替代正确解可接受测试特定实现风格，或solver能改reward写入逻辑
资源与时间区分agent deadline、verifier计算预算与outer deadlinetimeout当普通wrong reward；共享CPU噪声影响性能验收

Oracle仅证明至少一条已知解有效，不能证明问题无歧义或verifier完整。多个judge出自同一答案模板也不能视为独立证据；补充构造坏解、不同算法与clean rebuild比重复问同一个judge更有价值。

科学任务：把专家protocol变成可观察验收

ScienceIDE把专家知识落到模块、输入输出、可观察行为和数值容差，再生成环境工厂；报告的2,812 tasks包括2,515 repair、295 implementation、2 acceleration，七类taxonomy并不表示七类等量生产。[10]

数值接近不等于科学结论成立

pointwise: |candidate − reference| ≤ absolute_tol + relative_tol × |reference| invariant: units / conservation / monotonicity / boundary conditions

Pointwise检查适合确定性数组或标量；invariant能接受不同实现而保留物理约束。近零参考值需要absolute tolerance；随机算法固定seed并考虑分布统计；不同CPU / 库导致的小差异不能被误判为推理失败。另一方面，最终指标一致也可能掩盖数据泄漏、错误单位或只针对测试输入硬编码。

任务有效性检查科学检查坏控制
数值程序repair导入、运行、输出schema边界值、误差、稳定性或守恒常数输出、错单位、仅修一个test
论文程序复现代码可跑、产物可读数据划分、核心metric、消融方向读取held-out答案、错误baseline、只重述结论
科学数据分析数据来源与预处理可追溯统计假设、图表与研究产物一致标签泄漏、错误聚合、无依据显著性
加速任务相同输入下结果正确固定硬件、编译、warmup与重复timing删计算、减精度超容差、缓存测试答案

ScienceIDE的repair reward可按 max(0, (r−f)/(1−f)) 计算，r为测试通过比例、f为faulty baseline比例；它奖励相对修复进展，须处理f=1的无有效缺陷情况。Timeout、构建故障与graded failure应分列。其bounded / filtered训练cohort的结果不能推出全科学领域有效。ProgramGym和BixBench 3也分别强调复现与研究产物，见下一章。

需求合成、闭环扩张与失败回收

NexForge / EvoSyn：覆盖扩张与预算调度分开

NexForge从需求出发补任务覆盖；EvoSyn用当前策略的不足调整generation space，同时决定已有space的采样预算。[7][8] 二者都需要固定留出集：若生成器与verifier一起演化，训练reward提升可能只代表学会迎合新增判定规则。

实际对照可分别设置固定空间 / 固定预算、只调预算、只扩空间、两者一起变化；固定基础policy、harness和训练tokens，报告逐family的覆盖、有效组比例与成本。难度应来自多策略受控rollout及专家分析；单一弱solver全失败既可能是真难，也可能是坏task。

DeepSeek V4.1：多角色生产与独立检查

§5.1.1描述task triplet、general失败回放和mock tool；coding侧把build、test、solve、independent inspect和repair loop拆成角色，以修复不可靠任务。[12] 角色分离减少同一路径自证，但如果各角色共享参考答案、判断模板或模型偏差，仍需独立测试和坏控制。报告承认自造任务能力不完美。

失败轨迹可以训练critic，但标签质量仍是上限

CoderForge公开成功与失败轨迹；SWE-Critix利用差异分析训练critic，报告all-test预测accuracy从57%到66%再到78%。[6][11] 这些标签来自特定测试协议，不能换成“真实正确率”。论文Table II中R2E子集SFT表现更差，说明跨源异质性必须分项看。

Execution-based检查与execution-free critic互补：后者可廉价做排序、预筛和预算分配，但可能偏好长解释或特定patch风格。保留小规模独立执行校准，检查false accept / reject、逐源泛化与reward hacking，再决定是否用critic替代昂贵验证。

Family / repo / time层留出优于只按issue ID去重；例如同仓库相邻commit可能共享目标函数，模板任务也可能暴露同一答案结构。CoderForge的issue / base revision去污是有用措施，但不能单独证明所有这些泛化层次。架构、mock fidelity、渲染和工具权限也需要控制，避免训练与真实执行语义不一致。

异质GRPO进一步需要看success-rate分布、零方差组比例、逐域advantage与轨迹长度。数据量增加而有效更新组减少时，优先校准任务和采样，再换算法。机制与公式见Agentic RL章节；训练mask见CPT / Midtraining。

  1. 选3类family：真实repair、需求implementation、科学protocol；固定train / validation / test，记录来源、repo和时间边界。
