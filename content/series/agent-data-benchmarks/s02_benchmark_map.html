02 · Benchmark map · Snapshot 2026-11-14

先按能力与产物选评测，再看分数

Benchmark不只有一条“难度轴”。函数生成、仓库修改、终端操作、浏览器交互、桌面状态与科学研究产物，需要不同环境和检查。经典评测适合定位基础缺口；前沿Agent评测进一步测长程执行、恢复、工具和真实产物。

函数 / 答案HumanEval、MBPP、GPQA
代码单元与知识保留
仓库 / 终端SWE-bench、DeepSWE、TB
多步工具与工程产物
环境状态WebArena、OSWorld、τ²
交互、权限、reset与恢复
专业研究 / 工作TB Science、BixBench、AA
专业知识、产物与完整验收

这是测量对象分类，不是单向能力等级。一个函数题可能非常难，一个GUI任务也可能短；不同环境不可用一个未经校准的总分排序。

把测量对象放回系统：科学任务合同定义待校准真值和容差；工业对照记录策略/环境/预算/失败；权限与攻击分clean/attacked；部署成本将失败与重试纳入分母。多维指标由任务需要选择，不能用更大的榜单总分替代这些验收。

Terminal-Bench、Science、Challenges怎样分工

Terminal-Bench 4.1：修复测量工具也会改变榜单

4.0官方说明删除8任务、修复19任务并保留66任务，agent timeout扩到8小时；合作方对修复数另有20项口径，旧快照保留该差异。[14] 4.1正式release随后修改全部66任务，重点涉及verifier、可复现性和anti-hacking；另提供63项CPU-only集合。[13]

# 官方4.1集合，示例命令；本文未运行
harbor run -d terminal-bench/terminal-bench@4.1.0
harbor run -d terminal-bench/terminal-bench-cpu@4.1.0

# 报告还需注明：agent/model、harness版本、budget、trials、sandbox

训练前后在相同4.1任务及verifier上重跑，才能解释收益。CPU-only集合、旧TB 2.x、当前4.x与AA采用的4.0都要写全；“Terminal-Bench分数”一个名字不足以比较。

TB Science 0.1：测专业执行，不只测科学问答

首版70题覆盖5领域，任务需要在终端使用专业知识完成可执行产物。提案到发布经历920 proposals → 464 approved → 386 PR → 70 release，各门槛不同，不能把approved当入库题量。官方评测采用每模型3 trials及native harness，结果包含模型与执行系统差异。[15]

科学任务须区分代码可跑、检查通过、复现某结果与产生新科学发现；TB Sci高分不能单独支持最后一项。构建、数据下载、verifier timeout及数值容差可能造成无声误判。下一版0.2在调研日仍是路线规划，不写成已发布版本。

Challenges：长时间项目交付，先比正确性与资源

首发Rust Compiler Speedup、Inference Engine Codegolf、WASM WebGL Renderer三项挑战，面向day-scale单项目；提交最终repo与完整自主执行logs，按各任务的正确性或性能协议验收。[16] 没有统一时间和资源上限，就不适合与固定budget的TB成功率直接合并。

对Challenges应列wall time、tokens / API cost、计算资源、人类介入、完整日志与产物revision；性能优化先过correctness gate，再按同硬件timing。一次项目成功并不估计某个广泛任务分布的pass@1。

HarborIndex：困难切片与迁移一致性

初版研究从54个adapter的6,627候选任务形成82题困难切片；当前Hub revision 5 / 1.4是80题。[17][18][19] 初版筛选漏斗用于解释方法，不能把82题原实验计数改成80再称同一结果。

选择困难切片能拉开前沿系统差异，也会受所用筛选模型、budget及失败定义影响。它不是总体真实用户任务分布，也不是通用潜在能力指数。看结果时同时看SWE、安全、科学、数学与优化分项。

统一框架能做还要验证报告中保留
统一task / job / reward格式原生harness与adapter的权限、工具、终止语义、timeout是否一致原生与迁移运行协议，paired差异
统一sandbox及资源配置文件交接、数据与依赖是否改变任务Image digest、reset、verifier revision
跨benchmark组织执行验收异常、reward hacking、难度选择偏差逐任务状态、错误归因、修订与重跑

当前提交要求每题至少5 trials，并为部分任务固定LLM ensemble judge配置。Judge模型、prompt与版本属于评测工具的一部分；测量工具更新后要保留旧快照或全量重跑。适配执行成功不证明所有环境语义一致。

DeepSWE的两个含义，以及SWE-bench家族

Datacurve DeepSWE v1.1：original tasks + behavioral verifier

Benchmark含113 original工程任务，来自91个repo，涉及TypeScript、Go、Python、JavaScript、Rust；采用mini-swe-agent，评估long-horizon工程修改。交付committed diff后，放到干净verifier环境执行行为测试并生成CTRF；不向solver提供future git。[22]

任务原创新写且不upstream，降低公开旧patch污染风险；“contamination-free”的团队表述不能证明每个模型从未见过全部相关材料。Behavioral tests比匹配参考patch更能接受替代正确实现，但仍会误收 / 误拒；团队的LLM audit不能替代独立真值。版本1.0与1.1的verifier修订要分别看。

Together / Agentica DeepSWE-Preview：RL模型 / recipe

这是2025-07的Qwen3-32B训练方案，采用约4.5k R2E环境。团队报告42.2% pass@1、71% pass@16、59% hybrid test-time scaling；三个数分别包含不同采样或选择预算。[23] 不能把它们当Datacurve benchmark成绩，也不能把pass@16写成单次成功率。

AA：综合指数怎样组合不同测量

AA在本文指Artificial Analysis。2026-11-14方法页为Intelligence Index v5.0.1，9评测按4类各25%组合。它仍使用Terminal-Bench 4.0，虽然TB官方最新为4.1；引用AA结果应保留AA自身版本。[27]

子项pass、Elo与rubric须经AA定义的尺度处理后组合，不能把原始分数直接相加。权重是测量设计选择，不是各能力在所有用户场景中的真实占比；总分相近的系统可能有不同专业缺口。

GDPval-AA、APEX-Agents-AA、EnterpriseOps-Gym-AA等在该页属于Additional Evaluations，不是本版9个指数成员。它们分别扩展专业产物、专业服务与企业工作流；例如EnterpriseOps使用resettable工具环境及SQL outcome检查，GDPval-AA使用pairwise Elo。名称带AA也不表示所有harness、judge与split等同原始benchmark。

AA一般多次重复后平均pass@1，不能把3 repeats当pass@3；API failure重试、output token上限、reasoning effort、tool access、成本与cache计量也属于协议。对私有题可以核对公开方法，但无法声称已在本站独立复现。

训练后仍保留基础评测

MMLU用于学科知识、GSM8K用于基础多步数学、IFEval用于程序可验证的指令遵循、GPQA用于专家级科学问答。它们适合检查Agent训练是否损伤基础能力，不能作为tool use、long-horizon执行或GUI成功的证据。HLE-Diamond与CritPt等更前沿知识 / 科学题的具体设置见AA表。

Pass@1、pass@k、pass^k和成本测量不同东西

指标含义必须同时报告
pass@1 / mean success一次独立尝试成功的比例；多次repeats可以平均估计它Tasks、trials、seed、budget与失败分母
pass@kk个样本至少一个通过，oracle可识别成功Sample budget、成功判定及是否可部署选择
pass^kk次都成功，衡量重复可靠性用户模拟、环境变化与尝试相关性
Best-of-k / verifier selection部署时由verifier或critic选一个候选Selector版本、验证成本、误判；不等于oracle pass@k
Rubric / Elo多个标准或成对偏好Judge、prompt、anchor、顺序随机化及幻觉gate
If independent identical trials have success probability p: pass@k = 1 − (1−p)^k; pass^k = p^k finite-sample pass@k estimate = 1 − C(n−c,k) / C(n,k)

公式第一行依赖独立同分布假设；真实Agent尝试共享prompt、工具或故障，通常相关。最后一行适用于n个独立采样中c个成功且n≥k的组合估计。若已全部执行3 repeats再平均success，它仍是pass@1估计，不是pass@3。

把正确性、有效性与运行成本拆开

固定发布题集的headline应保留全部任务分母；invalid task、infra fail、API error、agent timeout、verifier timeout与policy fail分别列出。另报告有效任务上的conditional success，用来解释环境影响，不能静默删除失败让headline上涨。修订题集后用新版本全量重跑。

cost per successful episode = total cost of all attempts / successful episodes cost = model input/output + tools + sandbox + verifier + environment build paired comparison: same tasks, policy budget, hardware and scoring

失败尝试也消耗预算；全部失败时该比值无定义，应报告0成功及总成本。Environment build可按明示规则摊销，并保留冷 / 热成本。输入与缓存token、client span与server span、重试和工具等待要去重；同时提供episode P50 / P95、任务加权bootstrap区间与逐领域结果。跨模型cache计费不同，token数不是统一美元或FLOPs。
