Runtime & scheduling · 2026-11-14

每次调度分配的是token计算与状态空间

请求输入长度不同、输出何时结束未知。服务系统要在有限token计算预算与缓存空间内，让已有请求继续，并让新请求进入。PagedAttention管理状态位置，continuous batching管理参与计算的请求，chunked prefill管理长输入的计算粒度。

先修Decoder prefill/decode与KV公式。本章解释调度；多设备通信和低精度见下一章。

Prefill 与 decode 的计算负载不同

prefill处理新输入的多个位置，建立各层历史状态；decode使用已有状态生成后续位置。prefill的矩阵批量通常更大，decode低batch常受权重/KV读取和层间launch影响；这只是常见瓶颈，不是“prefill永远compute-bound、decode永远memory-bound”的定律。长度、并发、MoE、kernel、精度和网络会改变瓶颈。

TTFT包含排队、输入预处理、prefix查找、prefill及首token产生；ITL描述输出token之间的间隔。一个长prefill占用设备，会干扰已有decode的尾延迟；过度偏向decode又可能让新请求等待。调度需定义SLO和公平性。

批处理方式行为局限
Static batching一组请求共同开始，通常等待组完成长度不齐、空槽与队首阻塞
Continuous / iteration-level batching每轮加入新请求、移除结束请求还受cache容量和每轮token预算约束
Chunked prefill长输入拆成多个前向片段，与decode交错切块过小增加调度/launch，TTFT可能变长；不是文本chunk/RAG
PD分离不同设备分别承担prefill/decode新增状态传输、路由与资源闲置，详见下一章

PagedAttention解决物理存储，数学仍读取逻辑历史

连续为最大长度预留KV会浪费空间；逐请求扩容也容易产生碎片。PagedAttention把逻辑历史分block，由block table指向非连续物理页，kernel按映射访问。它降低外部碎片和重复分配，不把完整attention改成稀疏attention。最后一页仍可能有内部浪费，元数据、预留与临时区也存在。

请求有T个已保存token，block size为B： 逻辑block数 = ceil(T/B) 实际分配token槽 = B·ceil(T/B)，末页浪费 < B 共享prefix时：按唯一物理block核算，不能把每请求逻辑长度直接相加

prefix共享可让多个请求读取相同不可变block；写入共享尾页时需要copy-on-write或等价机制。物理分页与FlashAttention的IO-aware计算不同，两者可组合。原论文[1]的吞吐收益是其模型、硬件、负载和延迟条件，不是当前vLLM的统一倍数。

Prefix复用与RadixAttention

共享系统提示、文档或多轮历史的请求可以复用已计算prefix。复用通常依赖完全匹配的token前缀以及模型权重、adapter、位置/模板、多模态内容和cache格式；语义相似或最后一句相同不能直接复用。此前缀是数值状态，不是知识库。

SGLang的RadixAttention以树组织不同请求的共享前缀，按匹配部分减少重算。固定v0.5.23实现中的match_prefix、evict与inc_lock_ref/dec_lock_ref分别负责匹配、回收与正在使用的节点保护。[2] [3]

源码入口和“已结束”不等于“立即删除”

matched = match_prefix(request_prefix)
inc_lock_ref(matched_node)       # 正在使用的cache不能随意evict
execute_remaining_input_and_decode()

权限域、租户和模型版本必须纳入cache命名空间。跨租户共享即使不直接暴露KV，也可能通过命中时延形成侧信号；是否允许共享应在威胁模型中明确。policy更新后，旧权重KV通常不能直接沿用为新策略的状态。

长短请求、工具暂停与混合状态

工具Agent在生成与CPU工具执行之间停顿。如果持续保留全部KV，会占用大量容量；如果回收，下一步需要prefix命中或重算。要测工具等待时间、cache保留时长、重算token和复用收益，不能只报运行中batch size。

Hybrid模型可能同时维护全局KV、SWA、卷积状态和递归矩阵。全局KV可按token页管理；递归状态通常是累计状态，不能默认在任意前缀处裁剪或复制。当前vLLM KV manager包含Mamba共享prefix checkpoint相关分支，说明恢复对象需专门支持，不证明所有混合架构兼容。基础机制见状态递推。

本文建议长短任务分桶、设置准入和排队上限，比较混合池与独立池；限流避免环境迟缓的长程请求无限积累。TP/EP、PD和异步rollout在后两章共同算账。

调度对照与理解检查

冻结硬件、模型版本、精度和真实输入/输出分布，对照prefix开关、chunk大小、并发和长短请求比例。分别报冷/热cache、TTFT、ITL/P95、goodput、抢占、重算、取消和端到端任务成功。若提升prefix命中是因为测试请求复制训练答案，需要先排除污染。

分页为什么不会自动缩小每token的KV字节？

它改变分配方式和共享，单个逻辑token的结构/格式仍由层、KV head、维度与dtype决定。压缩或量化才改变内容表示。

工具暂停后重新发同样prompt能直接复用吗？

要匹配token、权重/adapter和cache命名空间，且旧状态尚在；语义相同不保证token一致。若回收则需重算。
